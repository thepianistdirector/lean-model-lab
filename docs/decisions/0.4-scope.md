# Local 0.2–0.4 scope decision

Decision date: 8 September 2026. Owner: Lucas Santana; execution and integration owner: the active Astra root.

Lucas authorized continuation to a useful local version 0.4, a project inference model using at most 60 GB RAM and 12 compute threads, and a new 200 GB project-disk / 12-hour local allocation. This materially expands the implemented workflow beyond the single frozen 0.1 comparison. It does not authorize public publication or establish a successful efficiency result.

The original allocation is **CLOSED**. Its candidate remains frozen at `.cache/release-review-20260908-03`, including the failed quality/parity finding, failures, costs and evidence limits. New development uses new versioned contracts and attempt identities. It must not modify the original workload, evaluator meaning or recorded observations to make the old finding eligible.

## Recipe and measurement invariants

For new v2 studies, request count is a multiple of four from 4 to 1024; output budget is 32 to 128 tokens; sorted unique concurrency modes contain one to four integers from 1 to 8. The default generator reproduces the original prompts and answers. Relative arrival offsets, seed, burst size, queue capacity and optional deadline duration are frozen in the recipe. Canonical regeneration rejects altered prompts, answers, quality controls and arrivals. V1 remains its original 128 requests, 32-token ceiling and three-pair `[1, 4]` design.

The new paired schedule is an even two to eight pairs with AB/BA repeating, resolved once for execution, reservation, evaluation and recovery. Manifest validation must reject incompatible model/workload/runtime combinations and unapproved settings before inference. The selected measurement uses only its admitted subset of those software capabilities.

The exact-answer quality rule remains at least 95%, using every offered request in the denominator. Define queue-capacity meaning, offered observation window, request deadlines and latency SLOs before serving runs. A late admission does not reset a deadline measured from offered arrival. Rejected, timed-out, cancelled and missing requests remain visible; a lower accepted load cannot masquerade as equal offered work. Goodput counts only requests satisfying the declared per-request quality and latency conditions. Failed global quality/parity gates cannot become an unqualified efficiency gain through presentation.

Keep client timestamps, declared arrivals, engine telemetry and model timing summaries distinct. Native progress placeholders are not output tokens; real EOS IDs remain observable even with empty text. Unsupported engine admission, internal token timing, thermal or energy measurements remain unavailable. Token IDs, templates and workload identities must match the chosen comparison semantics before results enter a common family.

Development feasibility may inform a new recipe before it is frozen. Retain those observations and charges; do not present model selection or tuning on observed answers as protected confirmation. Preserve failed quality, parity and full-wall outcomes. Local aggregate hashes establish consistency with retained bytes, not independent execution or external authenticity.

Each runtime or browser acceptance requires an actual recorded observation on the exact artifact under review. Test fixtures remain labeled synthetic; no test count is substituted for an unperformed model, participant or external test.

## Public and human limits

This scope authorizes useful local development through 0.4. Public artifact authorization, author identity, supported native Tanduna publication/readback, qualified human methodology and interpretation, and a fresh external environment obtaining and executing the public artifact remain independent gates. An agent review, local subprocess, inspected hash chain or generated HTML page cannot supply those observations.

Bundle exports must retain scientific values and original provenance while documenting any permitted metadata redaction. Local identifying paths, private prompts and credentials are not publication material. Exact local candidate readiness is reported separately from public release readiness; outstanding gates remain visible even if all local software and runtime checks pass.
