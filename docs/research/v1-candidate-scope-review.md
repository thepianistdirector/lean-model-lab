# v1 candidate scope review — 8 September 2026

**Recommendation: keep the classical slicer as the first end-to-end infrastructure demonstration, and prioritize a bounded investigation of whether a small model-specific acceptance controller can predict when symbolically valid omission changes actual model task success.** Treat cache/compression interaction as a subsequent systems challenge, not the principal novelty claim. No new architecture, priority, conformal guarantee, training advance for the LLM, or successful finding is established by this review.

This is a research-design review, not an investigator report or campaign result. It inspects `docs/V1-CONTRACT.md`, `context_slice.py`, `structured_workloads.py`, `research_studies.py`, `recipes_v3.py`, `runner_recipe.py` and `intervention_evidence.py`. It makes no source changes and launches no model or training job. The same leaf was previously verified as GPT-6 Astra with high reasoning. Resource estimates below are planning ceilings, not measured runtimes or a fresh allocation.

The owner requires a substantive candidate investigation with actual native execution, causal ablations, complete costs and prospective confirmation. That does **not** require a proven discovery: a rigorous negative or inconclusive investigation, and a project-relevant replacement supported by evidence, are acceptable. However, three repetitions of the same demonstration are not three substantive findings. Completing a real study and establishing novelty are separate judgments.

The implemented `dependency-slice-v1` parses a tiny record language, resolves final assignments, computes a reference closure and retains original lines. This is useful, inspectable classical slicing. Its certificate deliberately covers symbolic dependency preservation, not model behavior. The independent interpreter already solves the entire restricted task without an LLM. Therefore, showing that fewer records produce shorter prompts, or that the interpreter preserves their answers, supplies infrastructure validation rather than an inference-mechanism discovery. Actual disagreement between full and sliced model responses could become a useful limitation result, but it needs a mechanism question, systematic counterexamples and strong comparisons to justify the second investigation gate.

The current prospective proposal is appropriately candid about overlap and changed-input quality. It is nevertheless too weak as the complete substantive investigation: it compares mainly with uncached full context, uses independently generated tables rather than reusable table trajectories, has no trained acceptance component, and currently transforms all prompts before service. Those facts matter for the proposed cache-aware controller, which would depend on the actual preceding slot state. They are capability gaps, not observed scientific failures.

This was a finite primary-source check, not an exhaustive novelty search. Repository pages are mutable and should be pinned before any implementation comparison. Nothing in this review licenses importing their code, models, datasets or claimed performance into the measured artifact.

The prioritized causal question is:

> Among contexts whose dependency slice is independently verified to preserve the record-language answer, can a small controller trained on real full-versus-sliced model outcomes identify useful omission opportunities on fresh tables better than a predeclared simple gate, without observed harm or losing the full-cost benefit?

This is a **new project hypothesis with substantial prior-art overlap and unverified novelty**. It probes a practical bridge from semantic certificates to model-specific behavior. It is not logically necessary for every possible future architecture with native logit-error bounds: failure here would refute this bridge, not the entire trained-certifiable-omission vision. The potentially informative result is where symbolic sufficiency, learned acceptance and economic benefit diverge, not a positive token-reduction percentage.

The smallest substantive implementation would add one registered, fixed-complexity controller, for example a depth-two decision tree trained by bounded empirical risk minimization. It would use a fixed feature list derived solely from the prompt and its checked dependency graph: chain length, retained-record fraction, relevant superseded-write count, source positions of retained records and total prompt size. Exclude expected answers, raw key/value identities, seed, request ID and confirmation outcomes. Bind the resulting JSON parameters to the exact feature extractor, checkpoint, tokenizer and training record hashes. The runtime emits the original prompt or its certified slice; it never substitutes a symbolic answer. A malformed input or failed certificate returns full context.

This is actual **controller training**, if executed and traced. It is not LLM training, representation learning inside Qwen, or evidence of a new neural architecture. Root would need a registered training command, strict parameter schema, deterministic training trace, model-bound candidate loading and raw deployment decisions. Those capabilities are not supplied by the current slicer or by changing a proposal's descriptive text.

Train from four separately retained outcome classes: both correct, full-only correct, slice-only correct, and both wrong. The harmful-omission label is “full correct, slice wrong.” Never silently discard full-model failures: they remain in the offered quality denominator and can make the entire workload unsuitable for the frozen 95% gate. Fit the risk predictor on development outcomes, then choose an acceptance threshold on a **separate calibration population** from a predeclared finite grid. If no operating point satisfies the calibration rule, emit an always-full controller with an explicit refusal-to-compress result. Freeze parameters and threshold before confirmation.

The calibration rule can require zero observed harmful omissions and the existing quality floor, but with the proposed small samples it is only an empirical selection rule. Do not print a population-risk guarantee, “certified non-inferiority,” or a distribution-free confidence claim without implementing the relevant method, assumptions and adequate sampling. Repeated queries from one table are dependent; split and analyze complete table trajectories, never scatter their rows across fitting, calibration and confirmation. Zero observed harm is not proof of zero risk. A model-bound controller transferred to the other checkpoint is uncalibrated under that shift and must be labeled accordingly.

The required primary comparisons are genuinely distinct:

| Policy | Question it answers |
| --- | --- |
| Always full, no analyzer | Does the candidate beat the unmodified model at the frozen quality floor and complete cost? |
| Always dependency slice | Is learning useful beyond unconditional omission? |
| Predeclared simple gate | Does the learned controller add information beyond a fixed rule such as slicing only direct, non-updated lookups? This rule is frozen before fitting. |
| Learned gate | Does trained acceptance improve the held-out quality/cost frontier? |
| Matched-record-budget selection, small adverse control | Are gains due to dependency preservation rather than merely shortening text? Actual token budgets remain separately reported. |
| Independent symbolic interpreter, non-LLM floor | Does this restricted application need a model at all? Its output is never injected into native generation. |

Do not give the always-full baseline candidate parsing/training costs. Charge those to the candidate, including feature extraction, candidate and reference tokenization where required, artifact loading, training/calibration label collection, failed runs and recovery. Report both deployment cost and the complete development-inclusive cost, with shared ancestor costs counted once. Reusing previously obtained full/slice outputs can support a labeled offline policy replay, but cannot stand in for actual online timing of the deployed gate. Under stateful caching, even the replayed selected output can be invalid if it came from a different cache history.

Freeze these decisive falsifiers before confirmation:

1. **Symbolic soundness:** one independently interpreted mismatch on a prompt accepted by the dependency certificate refutes that certificate's restricted claim. Stop the candidate, retain the counterexample and issue a new version if repaired.
2. **Certificate-to-model implication:** one full-correct/slice-wrong native response with a valid symbolic certificate refutes universal model-equivalence. This remains a finding even if a trained gate later avoids that case.
3. **Learnability:** the trained gate cannot improve on always-full, always-slice and the frozen simple gate at the common observed quality constraint, or declines nearly all slices. This defeats the proposed practical value of the learned bridge; it does not become a successful discovery because a model was fitted.
4. **Shortcut/generalization:** record reordering, near-key decoys, longer references or stale last writes preserve the interpreter answer but cause accepted harmful omissions on unseen tables. This refutes the claimed acceptance transfer. Do not retrain on these confirmation failures and relabel the rerun as confirmation.
5. **Economics:** preprocessing, label acquisition, training, tokenization, retries or tails erase the prescribed 5% full-wall improvement or breach the 10% tail limit. Shorter prompts alone do not rescue the claim.
6. **Baseline feasibility:** full context fails the unchanged 95% gate. Report that failure; do not lower the gate or filter hard tasks to produce a positive efficiency result. A predeclared one-time switch from 0.5B to 14B is a model-selection step whose costs remain visible.

For a finite first protocol, a defensible ceiling is 32 independent fitting tasks with paired full/slice outputs, 32 separate calibration tasks with paired outputs, and 24 fresh confirmation tasks with four primary policies in two balanced repetitions: **320 native completions before the small feasibility and adverse-control allowances**. These counts are a planning option, not an instruction to launch. The tiny controller and small calibration set support a diagnostic study with descriptive uncertainty, not strong rare-failure guarantees. The actual model, matrix, grouping and counts must be frozen after one bounded feasibility check and before confirmation. If the labels contain no meaningful contrast or every safe policy collapses to the same action, retain that result and stop; do not expand a search until an advantage appears.

Prefer the already admitted 0.5B model with at most two compute threads for feasibility. If its full-context quality fails and the predeclared alternate is affordable, use the already admitted 14B model with at most six threads. Keep one heavy job, behind the current queue, and the original shared allocation deadline. No new weights, package ecosystem, paid API, GPU or training cluster is needed. A possible remaining-time reservation is at most 20 minutes for native feasibility, 150 minutes for the primary study, 60 minutes for a separate challenge, and at least 90 minutes for root's reproduction/release obligations, in addition to the reported approximately 45-minute remaining main job. These are ceilings to reconcile with the original deadline, not promises that either checkpoint will fit. Use observed setup plus conservative per-request wall time to check the remaining matrix before confirming it. If it does not fit, choose a smaller explicitly diagnostic matrix before freeze, or report the substantive gate incomplete.

The cache-aware proposal is a useful **second challenge** if the primary controller supplies an informative result. The focused question is whether a quality-qualified policy should sometimes retain a longer warm prefix because slicing destroys reuse, and whether a cheap cost gate predicts that boundary on native CPU traces. CAPC and Distil make the basic interaction known; any contribution here is a measured transfer/limitation, explicit cache-state accounting and a challenge to the learned gate under changing system conditions. It should not be relabeled as an invention of cache-aware compression.

The existing generated workload is inadequate for this challenge because it makes a fresh table for every request. A new immutable generator/version would need shared table/query trajectories, interleaved new tables, appended updates and queries that move between different dependency closures. Keep the instructions and table before the changing query, preserve record order, and remain within the admitted 64-record/2048-token envelope. Split by whole table trajectory. Include first-use work, cache priming and record updates in the offered denominator. Do not reorder a trace merely to improve cache hits after seeing outcomes.

The minimum systems comparisons are full/no-cache, full/cache, dependency-slice/no-cache and dependency-slice/cache, plus the frozen learned or simple cost gate and a small matched-budget/cache adverse control. An append-only, cached-prefix-preserving suffix slice is a strong existing-method comparator if implemented; its omission weakens any claim of a new cache-aware method. Record actual tokenized inputs, native reused/new input counts, complete request latencies, preparation overhead and per-slot state transitions. The primary cost baseline must include **full context with caching**, not only the easier uncached full-context arm.

An estimated cost such as `analysis + tokenization + alpha * new_prefill_tokens` is a hypothesis, not measured saved time. Longer retained context can still cost more during decoding. Estimate reuse only against the actual previous committed prompt in that slot, bind the identity and reconcile it with native receipts. Do not assume both a full-context and a sliced-context cache coexist in one slot. A controller must not take the minimum from two counterfactual runs with different histories and present that as an executable online result.

There is also a concrete cold-start falsifier: a myopic “fewest new tokens” policy may select a slice on the first request, never create the reusable full-table prefix, and therefore never reach the warm-full regime it was supposed to exploit. Conversely, forcing a full primer may lose on fresh-table traffic. Charge either choice. A literal warm-prefix selector alone does not solve that sequential decision problem. The smallest useful test includes both repeat-heavy and novel/update-heavy trajectories with the same rules and one actual cache lineage. It need not introduce a larger learned sequential policy within this allocation.

Root would need explicit capability changes before this challenge: cache-enabled slicing comparators, a causal per-slot decision/state trace, state reset/priming semantics, a new shared-table workload version, and replay verification that uses past observed state. Current prompt-only transformations and pre-service preparation do not supply that stateful policy. Keep the slicer itself prompt-only; if a separate serving controller consumes cache metadata, declare and hash that interface rather than quietly giving the candidate expected answers or future outcomes.

For publication worth, a positive result needs more than a learned gate matching unconditional slicing on an easy grammar. Require an interpretable distinction from simple baselines, meaningful accepted coverage, retained full-cost advantage at the existing quality rule, an actual deployed confirmation run, an adverse transfer result and an exact-package reproduction. A negative result can be equally useful if it provides real-model counterexamples and shows why apparently strong certificates or gates fail: semantic closure, model behavior and cache economics must be measured separately. That supports a narrowly scoped technical report or benchmark contribution; venue acceptance and broad significance remain unestablished.

If only the classical slicer demonstration is finished, call it a platform milestone and leave the substantive gate open. If the trained-gate experiment is executed and cleanly refutes the proposed bridge, report that as the bounded investigation rather than inventing a discovery. If resources prevent native training-label collection, calibration and deployed confirmation, retain the candidate as a hypothesis. None of these outcomes establishes architectural novelty, LLM training progress or general natural-language compression guarantees.
