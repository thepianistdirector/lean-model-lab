# Compatibility and troubleshooting

The current candidate was developed on Linux x86_64 with Python 3.12.14. Its control CLI uses the Python standard library. The pinned CPU backend, model weights and plotting environment are separate dependencies with explicit identities and notices. Other operating systems, architectures and Python versions have not been validated by this campaign. An offline HTML report needs no model or backend.

## Versioned evidence

| Format | Contract |
| --- | --- |
| Study/attempt v1 | Retains the original 128-request synthetic comparison and its original evaluator. |
| Recipe/study v2 | Binds reviewed profiles, allocation, arrivals, offered denominators and cache controls. |
| Recipe/study v3 | Adds registered prompt interventions, prospective research protocol and changed-input quality/cost rules. |
| Controller artifact | Exact model/template-bound fitted parameters, label provenance and calibration decisions; embedded into deployment recipes. |
| Export provenance | Explicit original versus redacted derivative inventories, retained event chains and unchanged scientific report. |

Each format has a strict validator. Unknown or changed fields are refused where a schema requires exact keys. Reports and exports are derived from retained evidence; editing a report is not a migration. Preserve the producer archive for every study. Current report tooling supports the retained formats, but resuming inference requires the original implementation identity and unchanged recipe. A later implementation uses a new study; it never rewrites prior attempts.

Schemas and registered mechanisms are internal versioned contracts, not a promise that arbitrary Python imports remain stable. The documented CLI, frozen JSON formats and included rerun scripts are the supported interface for this candidate. No network API service is part of the package. Changes to data generation, evaluation or instruction wording require a new identity and explicit compatibility evidence.

## Diagnose a refusal

| Symptom | Meaning and action |
| --- | --- |
| Output already exists | Immutable artifact protection. Inspect the existing result; use a fresh path for a new operation. |
| Heavy-job lease held | Another owned preparation or study is active. Use the documented queue helper or wait; preserve a refusal if one was recorded. |
| Workspace/root error | Start from the extracted source root with `WORKSPACE.json`; keep study, setup, model and backend within that workspace. Nested working directories are refused. |
| Model size or hash mismatch | Check the exact profile and all listed shard hashes. Do not edit the manifest to accept different bytes. The retained obsolete 0.5B profile is not an acquisition target; use its corrected `-v2` successor. |
| Implementation/recipe mismatch | Use the retained original producing archive and frozen recipe for inspection/recovery/resume. New code needs a separately identified study. |
| Local derivative lacks its original predecessor producer | A redacted derivative from this allocation is present, but its original producer tree is missing from the active workspace. Restore the exact original study history alongside the derivative before continuing. A publication export cannot replace original local history. Preserve any failed admission receipt. |
| Retained prior same-recipe measurement | The same recipe was already measured in the retained local allocation history. A repetition may check reproducibility, but it cannot become a fresh untouched confirmation campaign. Keep official ineligibility and report descriptive repeated-cell checks separately. |
| Torn journal or unreconciled attempt | Run `inspect`, then the documented `recover-journal` and same-boot `reconcile` sequence. Preserve original files and partial observations. Resume creates a new attempt ID. |
| Allocation expired or boot changed | That monotonic allocation cannot resume. Preserve its result. A fresh experiment needs the operator's own new resource decision; do not change the old clock. |
| Quality/parity gate failed | This is a measured adverse result, not an installation failure. Inspect all requests, model output and costs. Do not lower the threshold or repeat until favorable. |
| Unsupported proposal capability | Catalog coverage does not imply implementation. Choose a registered mechanism or implement and review the missing bounded capability before native execution. |
| No calibration threshold accepted | `ALWAYS_FULL` is an explicit fitted refusal. Report its label/quality/cost evidence; it does not establish that every possible learned gate is impossible. |

To report a problem, retain the CLI and recipe SHA-256 values, Python/platform information, exact command, exit code, `inspect` output and relevant raw failure receipt. Remove operational private paths through the supplied exporter before sharing. Never include model weights or credentials in an issue. The [research runbook](RUNBOOK-V1.md) links the full supported recovery sequence.

## Interpret timing with coordinator overhead

Service envelopes and full-attempt wall time include coordinator scheduling and resource checks; they are not pure model-compute measurements. The retained producer synchronously traverses the counted workspace for its periodic disk-limit check after more than one second has elapsed. The [separate source check](research/reproduction-review/observer-source-check.json) binds the exact implementation. A larger extracted evidence tree can therefore be an operational timing confound; the reproduction does not establish how much of a timing change the traversal causes.

For a prospectively designed study, record the workspace footprint and concurrent activity alongside the model/runtime settings. Keep unrelated extraction and analysis activity outside the measured interval while retaining all study outputs and costs. Compare offered-denominator quality, latency-qualified counts and complete wall time, and report native-output differences separately. Reproducing output tokens does not require an identical timing ratio. Preserve the original producer and its resource checks during an exact reproduction; a changed monitor needs a separately identified, controlled validation.
